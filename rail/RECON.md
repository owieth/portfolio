## Contradictions with the brief

1. The README says GTFS `shapes.txt` "is checked first; if it covers most lines, OSM becomes the fallback rather than the primary source". There is no `shapes.txt` in this feed. The geOps mirror does not have one either. OpenStreetMap is the primary geometry source, not a fallback, and #479/#480 are on the critical path rather than optional.

2. `route_long_name` is empty on every route in the feed, not merely sparse. Any step that planned to fall back to it — naming a line with no number (#475) above all — has nothing to fall back to.

3. The README includes `route_type` 100–117 and separately excludes `EXT` special-event trains. Those overlap: `EXT` is `route_type` 117, 110 routes. The include rule has to be stated as a `route_desc` allowlist, or the exclusion never fires.

4. The feed carries 277 routes under foreign categories (`TGV`, `ICE`, `RJX`, `NJ`, `TER`, `RB`), most of which are French, German and Austrian services that touch Switzerland or do not enter it at all. The README's include list does not mention them, and "every Swiss train line" is not the same set as "every line in the feed".

5. `route_desc` `ZUG` — literally "train" — appears on 1 route, which is a category that carries no category. It has to be handled by name.

- `route_long_name` is set on 0 of 976 routes. It is not a fallback; it is not populated.
- `trip_short_name` averages 50 distinct values per route. It is the train number, exactly as the issue suspected — one per departure, useless as an identity.

So the per-operator answer is not "a different field" but "the same field, or nothing". There is no operator that hides the line number elsewhere, which means #475 is unavoidable rather than a nicety.

## 4. Is there a `shapes.txt`

- **Official feed** (`otd-fp2026-20260919`): no `shapes.txt`. Members: `agency.txt`, `calendar.txt`, `calendar_dates.txt`, `feed_info.txt`, `frequencies.txt`, `routes.txt`, `stop_times.txt`, `stops.txt`, `transfers.txt`, `trips.txt`.
- **geOps mirror** (`https://gtfs.geops.ch/dl/gtfs_complete.zip`, 194 MB): no `shapes.txt`. Members: `agency.txt`, `calendar.txt`, `calendar_dates.txt`, `feed_info.txt`, `frequencies.txt`, `routes.txt`, `stop_times.txt`, `stops.txt`, `transfers.txt`, `trips.txt`.
- **Eisenbahn-Streckennetz (BAV / swisstopo)** (`ch.bav.schienennetz`): line geometry for the Swiss network exists and is public, but it is a geodata layer keyed on the BAV line number, not on anything in the GTFS feed. Joining it would mean first recovering a BAV line number per GTFS route, which the feed does not publish except incidentally on funiculars. [Dataset](https://data.geo.admin.ch/browser/index.html#/collections/ch.bav.schienennetz).

**Neither GTFS source ships geometry.** The README has this the wrong way round: OpenStreetMap is the only practical source of line shapes, so #479 and #480 are the primary path and there is no GTFS fallback behind them. The BAV layer is a second-order option that costs a join the feed cannot currently support.
